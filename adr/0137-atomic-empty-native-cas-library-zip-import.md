# ADR 0137 — Ripristino ZIP completo CAS su store vuoto, transazione unica (#189/#139)

## Motivazione
Il backup offline #183 di tutti gli attivi in ZIP può essere creato ma non ripristinato in un browser nuovo in modo atomico: ripetere 40 insert singoli espone a restore parziale, collisioni, tombstone riattivate e false prove storiche. Questo incremento implementa un vero percorso di scrittura CAS async, senza montare l'editor live legacy.

## Protocollo
1. Solo tramite file input manuale nel root `?workspace=cas` (NON nel preview incorporato nel `LegacyFactoryApp`), leggere massimo 20 MB. Validare il ZIP v1 offline con `fflate.unzipSync` e un filtro applicato **prima della decompressione**: file esclusivamente `manifest.json` + `projects/ID-rREV.json`, niente duplicati, traversal, ZIP64 sentinel, entry extra, encryption o compressioni ignote; cap 128 KB manifest, 4 MB UTF-8 per project, 64 MB UTF-8 complessivi. Decodifica UTF-8 fatal, limiti 40 active e 256 metadata tombstone, max 16M caratteri JS RAW, hash SHA-256 per file, project ID e revisioni canonici. Il manifest e i file devono essere esattamente quelli del formato esportato da #183; nessun contenuto viene inviato in rete.
2. Eseguire un `readonly` preflight **truly empty** usando `openCursor` su tutto lo store CAS, dove **qualsiasi** record o tombstone vale come occupato; rifiutare il file prima dei consensi se non è vuoto. Dopo due conferme esplicite e il ricalcolo SHA dei ticket, NON fidarsi del preflight precedente: aprire UN `readwrite` IDB sullo store. Nella stessa transazione `openCursor` e, soltanto se nessuna riga esiste, schedulare `store.add` per TUTTI gli attivi senza `await` nei callback. Qualunque collisione, quota, storage fault o insert concorrente abortisce tutta la transazione; **solo `tx.oncomplete`** è ACK. No merge/overwrite, restore tombstone, retry o rebase implicito.
3. Il JSON RAW del progetto storico è mantenuto byte-esatto; i nuovi slot IDB partono da revisione **1**, senza fingere di importare una storia locale di revisioni. Le vecchie revisioni e le tombstone sono metadata SOLO nello ZIP e non diventano slot nativi. Un readback dopo l'ACK verifica ID/rev/raw ma se fallisce non si ripete il batch: la transazione è già stata confermata. L'utente sceglie manualmente i progetti dalla libreria senza automontare pipeline/Code Agent.

## Limiti di sicurezza
Il file ZIP può contenere testo sensibile, credenziali inserite dall'utente o vecchi receipts: NON si dichiara sanificato o cifrato. SHA-256 protegge l'integrità, non firma, autori, test passati, Codereviewer o consensi GitHub; la UI informa che si tratta di EVIDENZA STORICA. Non è una restore/merge automatica multi-device, non protegge da un writer legacy che scrive localStorage, non migra gli altri write path live a CAS async. L'operatore conserva offline lo ZIP. La verifica del digest non assicura che il file originale sia attendibile; il parser rifiuta qualsiasi entry fuori protocollo.

## Verifiche
Vitest: manifest/hash, injection di path/extra, ZIP64 sentinel, consenso, ticket corrotto, ack ambiguo, budget e niente localStorage/fetch. Chromium reale 2 tab: backup #183, import su contesto nuovo, commit batch rev.1/raw esatti, tombstone solo metadata, file alterato, import cancellato, tab rivale che popola o crea tombstone durante i dialoghi, nessuna scrittura legacy, reload. Factory CI/Pages/Installer candidate success sullo stesso main SHA prima della chiusura #189.

## Hardening del confine asincrono del ticket (#191)
La funzione di conferma non fa affidamento su `Object.freeze` del parser: il caller potrebbe costruire direttamente un ticket mutabile. Prima del primo `await` cattura e convalida copie immutable dei RAW e delle revisioni, e dei metadati tombstone con controllo di collisioni. Ogni SHA-256 si applica solo al RAW catturato; dopo tutti i digest, l'identità e il contenuto del ticket esterno devono ancora coincidere. Una mutazione durante l'attesa fa fallire l'import **prima** di invocare il writer; soltanto le copie già verificate attraversano il confine IndexedDB. Il writer conferma ancora esclusivamente via `tx.oncomplete`. Test Vitest con digest sospeso, RAW differente ma canonico, array sostituito, tombstone mutata e ticket mutable stabile. Non aggiunge firma/provenance del backup né migrazione dei writer legacy (#139).

## Preflight dell'export sul parser reale (#192)
La UI di backup #183 non consegna più ZIP compressi che superano il limite **20 MB** già richiesto da questo parser o che falliscono la validazione del proprio formato. Il builder della libreria rilegge il ZIP prodotto con `parseCasEmptyLibraryBackupZip` (solo in memoria, mai con il writer IDB), conservando i consensi e le garanzie di commit/empty-store invariati. Per dati Unicode poco comprimibili che producono ZIP troppo grande, si blocca il download e si indicano backup JSON per ogni progetto; nessuna falsa promessa di recuperabilità del ZIP completo. Non dimostra che il file sia salvato dall'utente.
